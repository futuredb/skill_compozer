# Recognize components and demonstrate the live screen

## Component and behavior map

While inspecting each original, identify functional regions as well as visual layers. Extend the reference package's existing components/behavior fields with stable component IDs, role, bounds, visual states, parent scroll container, axis, action target and evidence status. Recognize buttons, icon actions, tabs, segmented controls, toggles, inputs, search, dropdowns, sliders, selectable cards, horizontal carousels, vertical lists, accordions, navigation and sheets where supported by the image. Distinguish decorative marks from affordances: a progress track is not automatically a draggable slider.

Use visible clipping, repeated items, pagination and layout to infer scroll candidates; confirm actual overflow in the implementation. An inferred affordance is not proof of the original interaction. Keep observed appearance, inferred behavior and designed demo motion separate. Do not invent offscreen content, destinations or extra components just to animate them. If content is unavailable, preserve the visible reconstruction and record the limit; additional scenario content must be explicitly labeled as adaptation.

## Find and integrate animation from 21st

Before hand-writing demo motion, use the installed `21st:21st-cli-use` skill and its supported catalog tools/CLI to search 21st for animation patterns matching the recognized components. Search by concrete interaction and movement, for example animated tabs/active indicator, swipe carousel with snap, expandable card, bottom sheet, button press, input feedback or animated number. 21st is a component catalog, not a single runtime dependency: retrieve the selected component's source and add only the dependencies its integration actually needs.

Inspect promising candidates' previews and source before selection. Match interaction semantics, direction, travel distance, easing/spring character, gesture model, state preservation, clipping and mobile behavior. Prefer the candidate that can preserve the reference's existing geometry and composition; popularity or visual spectacle alone is not a match. Search related terms if the first results do not address the recognized interaction. Do not add unrelated animated decoration just because it is available.

Retrieve and integrate a suitable candidate into the live reconstructed component, not merely a list of links or recommendations. Adapt its motion mechanism to the reference's measured dimensions, custom curves, materials and real state/callbacks. Keep original typography, icons, colors and contour assets unless the task requires changes; remove catalog demo branding, placeholder content and unnecessary wrappers. Reuse compatible installed motion dependencies and avoid introducing parallel animation engines for the same effect. Preserve the source license/attribution in code or provenance files, not as visible prototype chrome.

Record the catalog URL, author/component ID, source URL or retrieval identifier, license, dependencies, target component ID, chosen behavior and adaptations in the reference package and handoff. Keep downloaded source/provenance with the reusable code package so future library reuse does not require rediscovery. A static reference cannot prove the chosen animation was in the original: label it as designed adaptation even when supplied by 21st.

If CLI access requires authentication, use available catalog metadata and the author's explicitly linked public source when accessible. Do not claim retrieval or installation without actual source access. If access, license or compatibility prevents reuse, or no candidate fits after a focused search, record the reason and implement the closest appropriate behavior with the existing stack. Do not stall the reconstruction or force an inaccurate animation to satisfy catalog usage. Hosted AI generation is optional, not required; use it only under the 21st skill's access rules.

Verify the integrated component's actual behavior, cancellation, reduced motion, touch/keyboard interaction and stable still frame. The demo runner and manual interactions must drive the same state; imported autoplay or gesture handlers must not compete with the runner, nested scroll containers or the outer multi-screen strip. Disable added animation in calibration routes.

## Implement behavior before choreography

Export reusable components with data/state and callbacks. Real user interactions and the demo must share the same action/state functions. A press must change actual selected state, open its implemented destination or produce a supported local result; do not merely flash an overlay while the component stays inert. Keep demos local with synthetic data: no real submission, payment, external navigation or persistent user-data mutation. Limit the behavior to the reference or approved scenario.

- **Vertical scrolling:** scroll the actual overflow container, with fixed/sticky controls retained and readable pauses at relevant items. Measure bounds and clamp destinations. Do not translate the whole screen to fake a scroll.
- **Horizontal galleries:** move the actual horizontal viewport to a supported next item, respecting snap positions, card peeking and end bounds. Keep inner gallery scrolling separate from a multi-screen preview strip.
- **Presses/selections:** use a short pressed state plus the normal handler and meaningful state transition. Match subtle feedback to the reference's material and geometry; no generic pulse on every element.
- **Inputs/search:** visibly fill an actual controlled input with plausible synthetic data, keeping value, validation and dependent UI synchronized. Simulated typing may progress by characters or short chunks; do not animate static text over an unchanged field. Do not force focus/open the device keyboard during autoplay. Manual focus and typing work normally.
- **Toggles/tabs/sliders:** change the actual state or value, update dependent content, and animate only meaningful transitions. Preserve appropriate semantic elements and accessible state.
- **Navigation/sheets/accordions:** use only implemented destinations and supported states; preserve data and scroll position where appropriate. A screenshot alone does not establish original easing, gestures or timing.

## A short, legible demonstration

After faithful static calibration, create one coherent demonstration for the staged preview by default. Select relevant supported actions; do not run every action type on every screen. Begin with a readable still state, demonstrate a brief sequence, then settle on a useful end state. As a starting point allow roughly 0.8–1.5 seconds to inspect a state, 120–220 ms for press feedback, and 350–700 ms for a scroll/transition; tune to distance and legibility instead of treating these as source measurements. Avoid gratuitous entrance animation, constant motion or simultaneous unrelated actions.

Represent the sequence as data (for example step ID, screen/component ID, action, value/destination, wait condition, settle time). Implement a reusable cancellable runner separate from the screen component. Wait for mounted targets, fonts/layout and the previous action's completion; use bounded waits and stop with a recorded reason if a target is unavailable. Clean up timers, animation frames and listeners on cancellation/unmount. Do not force a new animation dependency if the project's existing stack or native browser animation/scroll APIs suffice; verify any library actually used.

In the staged preview, autoplay once after readiness and an initial pause, only if the user has not interacted. Do not loop or repeatedly reset product state. Pointer/touch input, wheel, keyboard input, focus into a product field, or Escape cancels the runner immediately and leaves the current state under user control. Pause while the document is hidden; resume only if the session remains untouched. Avoid focus stealing and excessive live-region announcements. Under prefers-reduced-motion disable autoplay and animated scrolling/typing; retain normal manual interactions.

Keep the existing no-operator-controls contract: no play panel, scenario buttons, synthetic hand or cursor effect. Pressed-state feedback is enough to indicate simulated taps. Support explicit `?demo=0` for an inspectable still staged preview and `?demo=1` for a fresh demonstration on page load; reduced-motion and user interruption still take priority. The default calibration routes always disable the runner, timers and added motion, regardless of demo parameters.

For multi-screen references, retain all live surfaces. Sequence actions on one screen at a time; implemented navigation scrolls the outer strip to the destination without unmounting siblings. Inner list/gallery scrolling must never move the outer strip accidentally. A `?screen=` deep link starts from that screen and must not immediately jump back to the first screen. Allow the user to take over without losing field values or gallery position.

## Verification and library evidence

Verify in the actual browser at desktop and mobile sizes: correct component identification, real overflow and scroll targets, press outcomes, input values and dependent state, gallery bounds, readable timing, interruption during a running step, no duplicated handlers on rerun, reduced-motion behavior and unchanged static calibration. Check that a demo cannot trigger real external actions. Finish with the existing neatness/symmetry/shape audit on the still frame and important animated states. Record unsupported or unverified behavior honestly.

Save the component map, demo sequence/runner paths, initial and final states, supported actions, route parameters, verification and limitations in the reference package and code handoff. Add a demo section to the library entry with routes and evidence paths. Store captured motion evidence only when actually recorded; never label a screenshot as evidence of timing. Keep the library source/result slider static with the faithful calibration. Its preview icon opens the staged screen with the demo available; do not animate every library card. Preserve the text-free gallery and use its existing renderer/validator.
